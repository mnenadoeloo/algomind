> Версия 0.2
> Нумерация: [шаблон Reliable ML](https://github.com/IrinaGoloshchapova/ml_system_design_doc_ru/blob/main/ML_System_Design_Doc_Template.md). Параметры пилота — плановые допущения до набора участников.

## 1. Цели и предпосылки

### 1.1. Зачем идём в разработку продукта?

#### Бизнес-цель

Подготовка к алгоритмическим секциям собеседований (LeetCode-подобные задачи) - массовая потребность разработчиков. Существующие подходы имеют системные проблемы:

| Подход | Проблема |
|---|---|
| Решебники / разборы на LeetCode, YouTube | Читаешь готовое решение -> иллюзия понимания, навык не формируется |
| Общий чат-бот (ChatGPT и т.п.) | Выдаёт ответ сразу, не ведёт диалог-обучение, не помнит прогресс, может уверенно ошибаться в сложности |
| Репетитор / менторство | Дорого и плохо масштабируется |
| Самостоятельная практика | Нет обратной связи, непонятно, какие темы проседают |

**Цель продукта:** превратить подготовку из «прочитал ответ» в «понял логику и закрепил навык» — с персонализацией по слабым местам.

#### Почему станет лучше от применения ML

- LLM способна вести **сократический диалог**: оценивать, где пользователь запутался, и давать подсказку нужной глубины — классическими правилами это не закодировать.
- Анализ **произвольного кода пользователя** (идея, баги, граничные случаи, сложность) — задача понимания кода.
- Классификация задач и ошибок по **темам/паттернам** позволяет строить профиль навыков и персональный план.

#### Что считается успехом (продуктовые и ML-метрики)

| Уровень | Метрика | Целевое значение (MVP) |
|---|---|---|
| Продукт | Доля пользователей, решивших задачу самостоятельно с подсказками (без показа полного решения) | ≥ 60 % |
| Продукт | Дополнительный рост решаемости по исходной слабой теме относительно контроля за 2 недели (разность изменений, п. 3.1) | ≥ 15 п.п. |
| Продукт | Retention D7 | ≥ 25 % |
| ML | Точность определения временной/пространственной сложности (на размеченном наборе) | ≥ 85 % |
| ML | Доля подсказок, не раскрывающих полное решение (LLM-judge + ручная проверка выборки) | ≥ 95 % |
| ML | Точность определения темы задачи/ошибки (accuracy по тегам) | ≥ 80 % |
| ML | Доля корректных вердиктов о правильности решения пользователя (с учётом запуска тестов) | ≥ 90 % |

### 1.2. Бизнес-требования и ограничения

#### Бизнес-требования

1. Пользователь вводит условие задачи (текст/ссылка) и получает **пошаговое сопровождение**: уточнение условия -> идея -> структура данных -> алгоритм -> реализация.
2. Уровень подсказки **регулируется**: по умолчанию - наводящие вопросы; полное решение выдаётся только по явному запросу после попыток.
3. Для любого решения пользователя система выдаёт **оценку сложности** (time/space) с обоснованием и указывает более оптимальные подходы.
4. Система хранит историю и строит **профиль навыков** по темам (массивы, графы, DP, жадные, два указателя и т.д.).
5. Система рекомендует **следующие задачи** под уровень и слабые места.
6. Поддержка русского и английского языков, языки кода - Python, затем другие.

**Бизнес-требование к пилоту:** 40 студентов старших курсов и начинающих Python-разработчиков, готовящихся к алгоритмическим собеседованиям; 4 недели, две группы по 20 человек. Проверяем пользу персонального плана относительно контроля: дополнительный прирост ≥ 15 п.п., решаемость с подсказками ≥ 60 %, D7 ≥ 25 %, выполнение порогов качества и бюджета. Процесс и правило решения — п. 3.

#### Бизнес-ограничения

| Ограничение | Значение / допущение |
|---|---|
| Бюджет на инференс | ≤ $0.10 на сессию разбора одной задачи в среднем; расчёт ниже |
| Латентность | p95 времени до показа проверенной подсказки ≤ 15 с; общий дедлайн 15 с, затем статический ответ |
| Команда | учебный проект, 1 разработчик, срок — семестр курса |
| Данные | только открытые/легальные источники условий задач; не копируем закрытые базы платных платформ |
| Приватность | код и история пользователя не передаются третьим лицам, кроме LLM-провайдера; хранение — с возможностью удаления |
| Безопасность | исполнение пользовательского кода только в изолированной песочнице с лимитами CPU/RAM/времени и без сети |
| Надёжность | допустима деградация: при недоступности LLM — отдаём статические подсказки/теги из базы |

#### Оценка стоимости сессии

Сессия — разбор одной задачи, планово 6 ответов. Генератор и guard — Haiku 4.5, $1 / млн входных и $5 / млн выходных токенов ([Claude API pricing](https://platform.claude.com/docs/en/about-claude/pricing), проверено 04.11.2026). Расчёт без скидок за кэширование:

| Вызовы за сессию | Входные токены | Выходные токены | Стоимость |
|---|---:|---:|---:|
| 6 генераций: по 4 000 входных (инструкции, условие, RAG, код, история) и 400 выходных | 24 000 | 2 400 | $0.036 |
| 6 guard-проверок: по 1 500 входных и 100 выходных | 9 000 | 600 | $0.012 |
| Классификация и итоговый анализ суммарно | 5 000 | 1 000 | $0.010 |
| Итого без повторов | 38 000 | 4 000 | $0.058 |

Повторная пара «генерация + guard» стоит $0.008. Две дополнительные пары за сессию дают $0.074; по две на каждый из шести ответов — $0.154. Поэтому исходные $0.05 заменены целью среднего $0.10. Это оценка, не замер: история и код могут быть длиннее. В пилоте считаем все фактические токены, повторы и ошибки, среднее и p95 стоимости; длинные сессии показываем отдельно. Песочница, БД и индекс учитываются отдельно от инференса.

#### Что считается «успешным MVP»

Пользователь решает 3 задачи подряд, получая только подсказки, и после этого видит корректный профиль слабых тем.

#### Риски

| Риск | Митигация |
|---|---|
| Галлюцинации в оценке сложности / ложный вердикт | Проверка решения запуском тестов в песочнице; эталонные решения и сложность для задач из базы; self-consistency |
| «Протекание» полного решения в подсказке | Многоуровневая система подсказок, guard-проверка выхода (LLM-judge), тесты на утечку |
| Задача пользователя вне базы -> нет эталона | Генерация тестов + сверка с несколькими независимыми решениями LLM; пометка «низкая уверенность» |
| Рост стоимости | Кэширование, маршрутизация простых запросов на меньшую модель |
| Небезопасный код пользователя | Песочница (контейнер, seccomp, без сети, лимиты) |

### 1.3. Что входит в скоуп проекта / итерации, что не входит

#### Итерация 1 (MVP, текущая)

**Входит:**
- Диалоговый разбор одной задачи с тремя уровнями подсказок (направление -> идея/структура данных -> псевдокод).
- Разбор решения пользователя на Python: корректность (запуск на тестах), оценка time/space сложности, граничные случаи.
- Базовая база задач (~100–200 задач) с тегами тем, сложностью и эталонной оценкой.
- Простой профиль навыков (статистика попыток и подсказок по темам) и подбор задач по слабой теме для пилота.
- Интерфейс: CLI или Telegram-бот / простое веб-приложение (уточняется).
- Набор для оффлайн-оценки качества (golden set) и отчёт по метрикам.

**Не входит (в этой итерации):**
- Mock-интервью с голосом/видео и оценкой soft skills.
- System design и behavioral-секции собеседований.
- Языки кроме Python.
- Интеграция с LeetCode/Codeforces через API и автоимпорт истории посылок.
- Мобильное приложение, платежи, соцфункции (рейтинги, друзья).
- Дообучение собственных моделей (используем готовые LLM + промптинг/RAG).

#### Дальнейшие итерации (roadmap)

1. Итерация 2: расширение адаптивного плана тренировок, spaced repetition по паттернам.
2. Итерация 3: дополнительные языки, mock-интервью в текстовом формате.
3. Итерация 4: интеграции с внешними платформами, персонализация на основе эмбеддингов задач.

### 1.4. Предпосылки решения

#### Источники данных

| Данные | Источник | Назначение |
|---|---|---|
| Условия, теги, сложность задач | Открытые датасеты (напр. наборы задач Codeforces/открытые LeetCode-подобные датасеты на HuggingFace), собственная разметка | База задач, RAG, рекомендации |
| Эталонные решения и тесты | Открытые решения, собственные + проверка запуском | Верификация, оценка сложности |
| Логи сессий пользователей | Собственный продукт | Профиль навыков, оценка качества, улучшение подсказок |
| Размеченные примеры «код -> сложность» | Ручная разметка + синтетика с проверкой | Оценка точности модуля сложности |

#### Технические предпосылки

- Основа — **LLM через API** (Claude Haiku 4.5 (`claude-haiku-4-5-20251001`, кандидат для пилота; допуск после итоговой оценки на holdout)) с промпт-инжинирингом и tool use; обучение с нуля не требуется.
- **RAG** по базе задач и конспектам алгоритмов/паттернов: поиск похожих задач и типовых приёмов.
- **Песочница** для запуска кода (Docker/gVisor, лимиты) — источник «ground truth» для корректности.
- Хранилище: PostgreSQL (пользователи, попытки, профиль) + векторный индекс (pgvector / Qdrant) для поиска задач.
- Python-стек: FastAPI/aiogram, pydantic, pytest, ruff, pre-commit.

#### Допущения

- Пользователь готов вести диалог, а не получать мгновенный ответ.
- Качества современных LLM достаточно для разбора задач уровня Easy–Medium; Hard — с пониженной уверенностью.
- Оценка сложности может проверяться эмпирически (замер роста времени на входах разного размера) в дополнение к LLM-анализу.

#### Близкий аналог

[CS50.ai / CS50 Duck](https://cs50.readthedocs.io/cs50.ai/) направляет студента к ответу без выдачи готового решения. Статья [Teaching CS50 with AI (SIGCSE 2024)](https://cs.harvard.edu/malan/publications/V1fp0567-liu.pdf) описывает внедрение на курсе и обратную связь студентов. Это пример применимости формата, но не доказательство эффекта персонального плана AlgoMind: аудитория и задачи отличаются, нужен собственный контролируемый пилот.

#### Бейзлайны для сравнения

1. Общий чат-бот без специального промпта («реши задачу»).
2. Тот же LLM + системный промпт «подсказывай, не раскрывая решения» без RAG и верификации.
3. Правила на тегах (статические подсказки по теме).

## 2. Методология

### 2.1. Постановка задачи

#### Формальная постановка

Система — композиция нескольких ML-задач вокруг LLM:

1. **Генерация подсказки уровня *k***. Вход: условие задачи *P*, история диалога *H*, код пользователя *C* (опц.), уровень подсказки *k* ∈ {1,2,3}. Выход: текст *h*, который продвигает пользователя, но не раскрывает решение выше уровня *k*.
2. **Оценка решения.** Вход: *P*, *C*. Выход: вердикт (верно / неверно / неоптимально), список проваленных граничных случаев, оценка сложности (T, S) с обоснованием, замечания.
3. **Классификация темы/паттерна.** Вход: *P* и/или *C*. Выход: множество тегов тем (multi-label).
4. **Оценка уровня навыка.** Вход: история попыток пользователя. Выход: вектор уверенности по темам *s ∈ [0,1]^T*.
5. **Рекомендация следующей задачи.** Вход: профиль *s*, база задач. Выход: ранжированный список задач с целевой сложностью около «зоны ближайшего развития».

#### Тип задачи

Условная генерация текста (LLM + RAG), классификация (multi-label), оценка кода по ground truth из исполнения, ранжирование/рекомендации.

#### Критерии качества и валидация

- **Оффлайн — настройка:** golden set из ~100 задач с размеченными тегами, эталонной сложностью и типичными ошибочными решениями используем для выбора модели, промптов, RAG и guard, а также регрессионных проверок. Результат на нём не считаем итоговой оценкой качества.
- **Оффлайн — итоговая оценка:** отдельный holdout из ~50 других задач с тем же составом разметки и покрытием тем и сложности. До настройки фиксируем разбиение по семействам задач: переформулировки, переводы, варианты одной задачи и все связанные решения/диалоги остаются в одном наборе. Holdout и его эталоны исключаем из RAG, примеров в промптах и настройки; также исключаем задачи итогового теста пилота. После фиксации модели, промптов и конфигурации считаем на holdout метрики из п. 1.1, включая LLM-judge на утечку с ручной проверкой выборки; одинаковый holdout используем для бейзлайнов. Если по результатам меняем систему, этот набор становится набором разработки, а для новой итоговой оценки собираем новый holdout. Неизвестное пересечение с предобучением внешней LLM остаётся ограничением оценки.
- **Онлайн (пилот):** персональный план vs фиксированный набор задач при одинаковых подсказках; протокол и критерии — п. 3.
- **Регрессия:** прогон golden set при каждом изменении промптов/модели.

#### Мониторинг (план)

Доля показанных полных решений, доля 👎, латентность, стоимость на сессию, расхождение вердикта LLM и результата тестов, дрейф распределения тем.

### 2.2. Блок-схема решения

#### Общая архитектура

```mermaid
flowchart TD
    U[Пользователь] -->|задача / код / вопрос| UI[Интерфейс: CLI / бот / веб]
    UI --> API[Backend API]

    API --> ORCH[Оркестратор агента]

    ORCH --> CLS[Классификатор тем и уровня]
    ORCH --> RAG[RAG: поиск похожих задач и паттернов]
    ORCH --> HINT[Генератор подсказок по уровням 1-3]
    ORCH --> EVAL[Анализатор решения]

    RAG --> VDB[(Векторный индекс задач и конспектов)]
    EVAL --> SBX[Песочница: запуск кода на тестах]
    EVAL --> CPX[Оценка сложности: LLM + эмпирический замер]

    HINT --> GUARD{Guard: не раскрыто ли полное решение?}
    GUARD -- нет --> API
    GUARD -- утечка или ошибка проверки --> RETRY{Повторов меньше 2 и есть время?}
    RETRY -- да --> SOURCE{Источник ответа?}
    SOURCE -- подсказка или пояснение рекомендации --> HINT
    SOURCE -- анализ решения --> EVAL
    RETRY -- нет --> STATIC[Проверенная статическая подсказка]
    STATIC --> API

    EVAL --> GUARD
    API --> UI

    API --> DB[(PostgreSQL: пользователи, попытки, профиль)]
    DB --> PROF[Профиль навыков]
    PROF --> REC[Рекомендатель задач]
    REC --> GUARD
    PROF --> ORCH
```

#### Сценарий «разбор задачи»

```mermaid
sequenceDiagram
    participant U as Пользователь
    participant A as Агент
    Note over U,A: Все генерируемые ответы, включая анализ и рекомендации, показываются после guard; лимит повторов и дедлайн как в п. 2.2
    participant R as RAG
    participant S as Песочница
    participant D as БД

    U->>A: условие задачи
    A->>R: похожие задачи, паттерны
    A->>U: уточняющие вопросы / подсказка ур. 1
    U->>A: идея или код
    A->>S: запуск на тестах
    S-->>A: результаты, время
    A->>U: обратная связь, подсказка ур. 2-3 или оценка сложности
    A->>D: запись попытки и использованных подсказок
    D-->>A: обновлённый профиль
    A->>U: итог + рекомендация следующей задачи
```

#### Ключевые решения

- **LLM — «мозг», детерминированные проверки — «истина».** Вердикты о корректности опираются на запуск тестов, а не только на мнение модели.
- **Guard на выходе:** весь генерируемый текст, включая анализ решения и рекомендации, проходит общий guard и буферизуется; пользователь получает ответ только после успешной проверки, без стриминга непроверенных фрагментов. Максимум две повторные генерации на запрос (три попытки всего); повтор возвращается к источнику отклонённого ответа. Для рекомендации с пояснением повторно генерируем только пояснение через генератор подсказок; выбранную задачу сохраняем. При повторе анализа сохраняем результаты песочницы, вердикт по тестам не меняем. Общий дедлайн 15 с включает RAG, генерации и проверки. При исчерпании времени/повторов или недоступности LLM возвращаем заранее проверенную статическую подсказку по теме; без известной темы — общий наводящий вопрос. Отклонённый текст не показываем.
- **Профиль навыков** — отдельный компонент, не зависящий от конкретной LLM.

## 3. Подготовка пилота

### 3.1. Способ оценки пилота

- **Пользователи:** 40 добровольцев из учебных сообществ, знающих основы Python, но не решающих уверенно Medium. Рандомизация по пользователям с балансировкой по входному результату, две группы по 20. Это разведочный пилот; размер пока не обоснован расчётом мощности.
- **Срок:** 4 недели: первая — набор и входная диагностика, вторая и третья — практика по 3 задачи в неделю, четвёртая — итоговая проверка и анализ. Диагностика завершается до рандомизации.
- **Процесс:** обе группы получают одинаковые интерфейс, сократические подсказки, guard и время практики. Экспериментальная группа получает задачи по слабой теме входной диагностики, контрольная — фиксированный сбалансированный набор без персонального плана. Слабую тему фиксируем до практики и не перевыбираем по итоговым результатам.
- **Проверка навыка:** до и после практики каждый решает по 3 задачи на каждую из четырёх тем (массивы, два указателя, графы, DP), без тьютора и внешних решений, с одинаковым лимитом времени. Разные формы заранее выравниваем по сложности, порядок форм балансируем между группами; тестовые задачи исключаем из практики и RAG. Успех задачи — прохождение скрытых тестов в песочнице.
- **Основная метрика:** для каждого участника считаем изменение доли решённых тестовых задач по исходной слабой теме. Эффект = среднее изменение в экспериментальной группе минус среднее изменение в контроле. Контроль учитывает общий эффект практики и регрессию к среднему. Показываем 95 % доверительный интервал с бутстрэпом по пользователям; попытки не считаем независимыми участниками.
- **Другие метрики:** доля участников экспериментальной группы, решивших хотя бы одну задачу практики с подсказками без полного ответа (знаменатель — все назначенные в группу); D7 — возврат на 7-й день после первой практики среди начавших; утечки, стоимость и задержка. Отток и пропуски показываем по группам. В основном консервативном расчёте пропущенные итоговые задачи считаем нерешёнными; отдельно приводим анализ по завершившим.

### 3.2. Что считаем успешным пилотом

Переходим к расширенному пилоту при одновременном выполнении условий:

1. Разность изменений ≥ 15 п.п., нижняя граница 95 % интервала выше нуля.
2. Решаемость с подсказками ≥ 60 %, D7 ≥ 25 % в экспериментальной группе.
3. Выполнены ML-пороги из п. 1.1; все подсказки пилота проверяем на утечки вручную, независимо от guard.
4. Средняя стоимость инференса ≤ $0.10 за сессию, p95 времени до проверенной или статической подсказки ≤ 15 с. Долю статических ответов показываем отдельно, чтобы задержка не скрывала деградацию.

Если интервал включает ноль или итоговую проверку прошли менее 80 % любой группы, результат неопределённый: оцениваем размер следующего эксперимента по наблюдаемой дисперсии, успех не объявляем. При нарушениях безопасности останавливаем пилот; при провале качества или бюджета дорабатываем компонент и повторяем оценку до расширения.

### 3.3. Подготовка пилота и ограничения

До набора фиксируем модель, промпты, задачи, тесты и схему рандомизации; выполняем регрессию на golden set, итоговую оценку на holdout после фиксации конфигурации и проверку изоляции песочницы. Получаем согласие на обработку кода и истории, обеспечиваем удаление данных. Разработчик отвечает за набор, поддержку и ручную проверку. Результат — метрики по группам с интервалами, затраты и решение о следующей итерации. Коммерческую эффективность и долгосрочное сохранение навыка этот пилот не устанавливает.
